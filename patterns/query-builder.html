Patterns

Query builder

Advanced search: a dense sentence builder for a shareable research set. It keeps condition rows honest — field, operator and value stay visible — and hands the set to the results toolbar, where Share (Link, Embed, API, Feed) and Save search live. One builder for the power tier, replacing both legacy tiers: the advanced form and the expert query language.

Why this layout

Four decisions and what each one answers for.

The builder takes the screen, as a dialog

A real query runs to six or more rows, one of which can hold hundreds of pasted identifiers, so the builder needs concentration and room. An extra-large dialog gives it both: the result list stays visible at the edges, which tells someone this is a mode they can leave, and the backdrop marks it as one. A page carrying a facet rail, a chip bar, a toolbar and twenty-seven cards is the least focused place on the site, so the builder does not sit inline above the results. modal-dialog--wide holds a condition row without a scrolling keyhole.

The count answers the question being asked

While building, the live question is "does my query work", and a count answers it in full. The list itself is a different question, answered by leaving. Rendering results inside the builder would mean a second implementation of a page that already owns sorting, paging, faceting and exporting — so the builder authors a query and hands it over, and a session that only ever watches the count is a successful session.

One exit, because nothing is pending

Every complete condition has already updated the URL, so there is nothing to apply and nothing to discard. That removes an apply and cancel pair, a dirty state, and the confirmation that follows it. Show results, Escape and the × all do the same thing.

The handoff lives on the results toolbar

The builder authors the durable research set someone will bookmark, embed, feed into a tool or send to a colleague — but taking it away is a set-level act, so Share (Link, Embed, API, Feed), Save search and Export sit on the results toolbar as one grammar, mirroring the record-level row (Cite, Share, Add to list). The builder holds the conditions and the count, nothing else: the exit bar answers the immediate question — does this set match anything, and can I inspect it now? Save search is also the honest answer to long pasted lists that outgrow a durable URL.

The dialog is a URL state

Opening it adds &advanced=1 to the address, and closing it removes that again. Reload then returns to the builder on the same query instead of a blank list, which matters most after an accidental navigation. Back goes to the previous URL state, whatever that address held. And the address can be sent to someone: pasting it opens the builder with the query loaded, which is the answer to "how did you get this list?".

The Link tab hands out a clean results address without advanced=1, because what someone shares is the search, not the fact that the builder was open while they made it. In production the address renders the open dialog: hx-push-url pushes it and the server sends the dialog open, so arriving needs no script. The kit needs one. Its dialog is a single shut element that query-builder.js opens when the address or a ?state= builder variant says to. Pushing the address as the dialog opens and closes is production's, so what the kit shows is the position, not the history.

The condition row

A condition row reads left to right: the field it asks about, a role where the field takes one, the operator, the value, and the row's actions. The role is a select like any other — Person, in any role, is any of, the names — because narrowing to editors is the same kind of choice as picking the operator, not an aside on the field name. The lanes belong to the list, not to the rows: the condition list is a three-track grid and every row borrows those tracks, so the field lane and the actions line up down the list without a single row stating a width. The lane is as wide as the longest field name in that list — no measurement to keep in sync — capped so one long name cannot reshape the editor. The operator sits at the width of its longest option and the value takes what is left. When the row runs out of room the field keeps the first line with the actions pinned to its right, and the role, operator and value drop to the next line as one phrase; a value moves whole rather than breaking apart, because it will not shrink below its own content. That threshold reads the width of the editor rather than of the screen, because a phone renders the dialog full-bleed and a desktop does not. The value is what the reader is saying, so the mechanics stay quiet beside it — no row numbers, no boxes. A person value is its people, as badges, with a badge-style Add a person after them: picking a person is the same act as on the results page, so it opens the shared searchable people checklist — the checkable rich rows settled on the people-search pattern page, which the works author filter adopts too — and the badges sit in the row rather than inside a text field, because the row's value is a set of records and not something typed. Every control carries a label naming its row, because identical selects without row-specific labels are unnavigable by ear. Every control in the row is the small size — form-select-sm and form-control-sm throughout — so the whole row sits at one 32px height and a query of six rows stays readable in one screen. Mixing the two sizes on one line is what puts a 38px control beside a 32px one.

Rows join with and, and nothing between them says so: the top level is always AND-joined, the heading above states it once — Show research output where all of these are true — and a word repeated between every pair only restates that heading. The hairline is the join. An or is the case that does need saying, and it belongs to a row, not to the top level. Open the row’s more menu and pick or…, and the row becomes a group reading …where any of these conditions is true. The word conditions does work there. A row’s own is any of lists values for one field; a group lists conditions. Drop the word and the two offers read the same.

The states

Five, and they live on the works page as template states rather than being copied in here — the builder is too large to duplicate without the copy drifting from the original. Each shows the dialog open over the list the query would have produced, so the page behind it is never blank.

  • builder-full-query — a query already assembled: free text, two person rows (a co-author query, not a list), a year range, an is not, and a pasted batch of identifiers.
  • builder-empty — a first visit. Add a condition and nothing else: the field chooser is what produces the operator list and the value widget, so the empty builder offers the one control that opens it.
  • builder-one-condition — arrival from an entity page or a filtered list: the scope is already a row, editable and removable like any other. The usual case, not an extra.
  • builder-or-group — the any of these group, one level deep. A group is a state of a row, so it occupies the row's slot and collapses back to a plain row when one alternative is left.
  • builder-no-results — a query matching nothing: the failing condition is marked in place, the submit reads No results, and nothing is auto-dropped.

The same states render inside the dialog, since both renderings include the same partials. The dialog's host page adds one of its own, facet-set-in-builder, for the sidebar case below.

The count, and what belongs beside it

The count is the answer the builder produces, and it lives on the one exit: the submit reads Show ± 1 280 results and carries the builder's only aria-live, so an updated count is announced without reading someone's own typing back to them. The rows are the readback. There is no apply and no cancel: every complete condition has already updated the URL, so the submit is the one exit, next to Clear all — clearing and showing results are both ways of leaving the query you have.

Exit bar

Nothing else is in this bar. The results toolbar owns the shareable artifacts; the exit bar owns the count and the one way to the result list. The count is an approximation — where the number comes from is the field contract's open question 9.

Dialog, panel, or page

One rule, so that neighbouring buttons don't behave differently for no reason.

ContainerContentAnchored toHere
Panel a short choice, or one thing to copy its button Add to list, Cite, Share, Save search, filter editor
Dialog a task needing the screen, or a consequence nothing Advanced search, Export, confirmations
Page a surface someone arrives at an address the result list, which the builder opens over and never replaces

Two consequences follow. Cite became a panel on 2026-08-10: it hands over one string and sits in the same action row as Add to list, which was already a panel, and two adjacent buttons where one anchors to itself while the other takes over the screen is a difference people feel without being able to name it. A dialog never opens a dialog: if something reachable from inside the builder outgrows a panel, the answer is a step inside the same dialog — a back arrow swapping the body, as the mobile filters tray already does.

When a facet cannot express the condition

A built condition can say things a checkbox list cannot: is not, a range, a pasted batch. Applied filters surface as chips either way (search & filtering, rule 4), and the facet whose dimension is held reports that instead of contradicting it with empty checkboxes.
