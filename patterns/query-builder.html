Query builder

Advanced search: a dense sentence builder for a shareable research set. It keeps condition rows honest — field, operator and value stay visible — and hands the set to the results toolbar. One builder for the power tier, replacing both legacy tiers: the advanced form and the expert query language.

Why this layout

The builder takes the screen, as a dialog

A real query runs to six or more rows, one of which can hold hundreds of pasted identifiers, so the builder needs concentration and room. An extra-large dialog gives it both: the result list stays visible at the edges and the backdrop marks the builder as a mode someone can leave. A page carrying a facet rail, a chip bar, a toolbar and twenty-seven cards is the least focused place on the site, so the builder does not sit inline above the results. modal-dialog--wide holds a condition row without a scrolling keyhole. The dialog keeps one shape whatever the query holds — header and footer pinned, the body scrolling between them — so the count and the exit sit in the same place with one condition as with twelve.

The handoff lives on the results toolbar

The builder authors the durable research set someone will bookmark, embed, feed into a tool or send to a colleague — but taking it away is a set-level act, so Share (Link, Embed, API, Feed), Save search and Export sit on the results toolbar as one grammar, mirroring the record-level row (Cite, Share, Add to list). Save search is also the honest answer to long pasted lists that outgrow a durable URL.

The dialog is a URL state

Opening it adds &advanced=1 to the address, and closing it removes that again. Reload then returns to the builder on the same query instead of a blank list, which matters most after an accidental navigation. Back goes to the previous URL state, whatever that address held. And the address can be sent to someone: pasting it opens the builder with the query loaded, which is the answer to "how did you get this list?".

The Link tab hands out a clean results address without advanced=1, because what someone shares is the search, not the fact that the builder was open while they made it. Production renders the address with the dialog open; the kit opens it with a script instead, so it shows the position, not the history.

The condition row

A condition row reads left to right: the field, a qualifier where the field has one, the operator, the value, and the row's actions. On Person the qualifier is the role, on Published in the kind of container, and it is a select like any other: narrowing to editors, or to journals, is the same kind of choice as picking the operator. The operator in turn decides the value's shape: is between turns one year into a pair, and is any of turns a select into a token list and a year into a comma-separated box.

The lanes belong to the list, not to the rows: the condition list is a three-track grid and every row borrows its tracks, so the field lane and the actions line up down the list without a single row stating a width. The field lane is as wide as the longest field name, capped so one long name cannot reshape the editor; the operator sits at the width of its longest option; the value takes what is left. When the row runs out of room, the field keeps the first line with the actions pinned to its right, and the qualifier, operator and value drop to the next line as one phrase. The value moves whole, because it will not shrink below its own content. That threshold reads the width of the editor, not of the screen, because a phone renders the dialog full-bleed and a desktop does not.

The value is what the reader is saying, so the mechanics stay quiet beside it: no row numbers, no boxes. A person, organization or project value is a set of records, not typed text — picking one is the same act as on the results page, so the Add button opens the shared panel settled on the people-search pattern page, and the crest marks a UGent person record. Every control carries a label naming its row, because identical selects without row-specific labels are unnavigable by ear. Every control is the small size, form-select-sm and form-control-sm, so six rows stay readable in one screen.

Rows join with and, and nothing between them says so: the top level is always AND-joined, the heading above states it once — Show research output where all of these are true — and a word repeated between every pair only restates that heading. The hairline is the join. An or is the case that does need saying, and it belongs to a row, not to the top level. Open the row’s more menu and pick or…, and the row becomes a group reading …where any of these conditions is true. A row’s own is any of lists values for one field; a group lists conditions — the word keeps the two offers apart.

The states

Five, and they live on the works page as template states rather than being copied in here — the builder is too large to duplicate without the copy drifting from the original. Each shows the dialog open over the list the query would have produced, so the page behind it is never blank.

  • builder-full-query — a query already assembled, at the size a real one reaches. Its two Person rows are a co-author query, not a list of alternatives: the or is the group.
  • builder-empty — a first visit. Add a condition and nothing else: the field chooser is what produces the operator list and the value widget, so the empty builder offers the one control that opens it.
  • builder-one-condition — arrival from an entity page or a filtered list: the scope is already a row, editable and removable like any other. The usual case, not an extra.
  • builder-or-group — the any of these group, one level deep. A group is a state of a row, so it occupies the row's slot and collapses back to a plain row when one alternative is left.
  • builder-no-results — a query matching nothing: the failing condition is marked in place, the submit reads No results, and nothing is auto-dropped.

The count, and the one exit

While building, the live question is "does my query work", and the count answers it: the submit reads Show ± 1 280 results and carries the builder's only aria-live, so an updated count is announced without reading someone's own typing back to them. The rows are the readback. Rendering results inside the builder would mean a second implementation of a page that already owns sorting, paging, faceting and exporting — a session that only ever watches the count is a successful session.

There is no apply and no cancel: every complete condition has already updated the URL, so nothing is pending and nothing gets discarded. Show results, Escape and the × all do the same thing, and Clear all sits beside the submit because clearing and showing results are both ways of leaving the query you have.

Exit bar

The results toolbar owns the shareable artifacts; the exit bar owns the count and the one way to the result list. The count is an approximation — its behaviour, and how exact it may be, is docs/wip/QUERY-BUILDER-ISSUE-04-count.md's question.

Dialog, panel, or page

One rule, so that neighbouring buttons don't behave differently for no reason.

ContainerContentAnchored toHere
Panel a short choice, or one thing to copy its button Add to list, Cite, Share, Save search, filter editor
Dialog a task needing the screen, or a consequence nothing Advanced search, Export, confirmations
Page a surface someone arrives at an address the result list, which the builder opens over and never replaces

A dialog never opens a dialog: if something reachable from inside the builder outgrows a panel, the answer is a step inside the same dialog — a back arrow swapping the body, as the mobile filters tray already does.

When a facet cannot express the condition

A built condition can say things a checkbox list cannot: is not, a range, a pasted batch. Applied filters surface as chips either way (search & filtering, rule 4), and the facet whose dimension is held reports that instead of contradicting it with empty checkboxes.
