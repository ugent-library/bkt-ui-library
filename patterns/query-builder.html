Patterns

Query builder

Advanced search: a dense sentence builder for a shareable research set. It keeps condition rows honest — field, operator and value stay visible — and keeps the handoff nearby as Link, Embed, API and Feed. One builder for the power tier, replacing both legacy tiers: the advanced form and the expert query language.

Why this layout

Four decisions and what each one answers for.

The builder takes the screen, as a dialog

A real query runs to six or more rows, one of which can hold hundreds of pasted identifiers, so the builder needs concentration and room. An extra-large dialog gives it both: the result list stays visible at the edges, which tells someone this is a mode they can leave, and the backdrop marks it as one. A page carrying a facet rail, a chip bar, a toolbar and twenty-seven cards is the least focused place on the site, so the builder does not sit inline above the results. modal-dialog--wide holds a condition row without a scrolling keyhole.

The count answers the question being asked

While building, the live question is "does my query work", and a count answers it in full. The list itself is a different question, answered by leaving. Rendering results inside the builder would mean a second implementation of a page that already owns sorting, paging, faceting and exporting — so the builder authors a query and hands it over, and a session that only ever watches the count is a successful session.

One exit, because nothing is pending

Every complete condition has already updated the URL, so there is nothing to apply and nothing to discard. That removes an apply and cancel pair, a dirty state, and the confirmation that follows it. Show results, Escape and the × all do the same thing.

The builder holds the handoff rail

The page is not only a way to reach results; it authors the durable research set someone will bookmark, embed, feed into a tool or send to a colleague. Link, Embed, API and Feed therefore stay visible beside the rows. The count and Show results stay in the pinned exit bar, because they answer the immediate question — does this set match anything, and can I inspect it now? Save remains visible in the handoff rail as the honest answer to long pasted lists that outgrow a durable URL.

The dialog is a URL state

Opening it adds &advanced=1 to the address, and closing it removes that again. Reload then returns to the builder on the same query instead of a blank list, which matters most after an accidental navigation. Back closes the dialog rather than leaving the page, which is what a full-screen overlay trains people to expect. And the address can be sent to someone: pasting it opens the builder with the query loaded, which is the answer to "how did you get this list?".

The Link tab hands out a clean results address without advanced=1, because what someone shares is the search, not the fact that the builder was open while they made it. In the prototype query-builder.js pushes and pops that parameter; in production it is hx-push-url and a server-rendered open dialog, so the address works with JavaScript switched off.

Two renderings, one source

Where someone arrives from decides the shape. The builder itself is two shared partials, search-advanced-conditions.html and search-advanced-actions.html, so neither rendering can drift from the other. Everything around it belongs to the host: each supplies its own heading, its own box and its own surface under the bar.

As a page

Arriving cold — a bookmark, a help page, a link from a colleague. There is no result list to preserve, so the builder gets a breadcrumb, a title, and a stable address to point at. You leave by the breadcrumb.

As a dialog over the results

Refining a list already on screen. The list must not be navigated away from, so the builder opens over it and the list stays visible at the edges. You leave by the ×, by Escape, or by Show results.

The dialog is modal-xl modal-dialog--wide modal-dialog-scrollable. Scrollable pins the header and the footer and scrolls only the body, so the count and the exit stay on screen however long the condition list runs — and the form has to sit inside the body rather than wrapping all three, or that flex chain breaks and the footer leaves the screen. modal-dialog--wide widens it past modal-xl, because a condition row carries a field, an operator, a value and sometimes a role.

The condition row

A condition row reads left to right: the field it asks about, a role where the field takes one, the operator, the value, and the row's actions. The role is a select like any other — Person, in any role, is any of, the names — because narrowing to editors is the same kind of choice as picking the operator, not an aside on the field name. The lanes belong to the list, not to the rows: the condition list is a three-track grid and every row borrows those tracks, so the field lane and the actions line up down the list without a single row stating a width. The lane is as wide as the longest field name in that list — no measurement to keep in sync, and the same width in the dialog as on the page — capped so one long name cannot reshape the editor. The operator sits at the width of its longest option and the value takes what is left. When the row runs out of room the field keeps the first line with the actions pinned to its right, and the role, operator and value drop to the next line as one phrase; a value moves whole rather than breaking apart, because it will not shrink below its own content. That threshold reads the width of the editor rather than of the screen, since the same partial is narrower as a page column than as a dialog. The value is what the reader is saying, so the mechanics stay quiet beside it — no row numbers, no boxes. A person value is its people, as badges, with a badge-style Add a person after them: picking a person is the same act as on the results page, so it opens the same searchable checklist the works filter bar opens for its person filter, and the badges sit in the row rather than inside a text field, because the row's value is a set of records and not something typed. Every control carries a label naming its row, because identical selects without row-specific labels are unnavigable by ear. Every control in the row is the small size — form-select-sm and form-control-sm throughout — so the whole row sits at one 32px height and a query of six rows stays readable in one screen. Mixing the two sizes on one line is what puts a 38px control beside a 32px one.

Rows join with and, and nothing between them says so: the top level is always AND-joined, the heading above states it once — Show research output where all of these are true — and a word repeated between every pair only restates that heading. The hairline is the join. An or is the case that does need saying, and it belongs to a row, not to the top level. Open the row’s more menu and pick or…, and the row becomes a group reading …where any of these conditions is true. The word conditions does work there. A row’s own is any of lists values for one field; a group lists conditions. Drop the word and the two offers read the same.

The states

Three, and they live on the standalone page as template states rather than being copied in here — the builder is too large to duplicate without the copy drifting from the original.

  • built — a query already assembled: free text, two person rows (a co-author query, not a list), a year range, an is not, and a pasted batch of identifiers.
  • advanced-empty — a first visit. Add a condition and nothing else: the field chooser is what produces the operator list and the value widget, so the empty page offers the one control that opens it.
  • advanced-group — phase 2's any of these group, one level deep. A group is a state of a row, so it occupies the row's slot and collapses back to a plain row when one alternative is left.

The same states render inside the dialog, since both renderings include the same partials. The dialog's host page adds one of its own, advanced-condition, for the sidebar case below.

The count, and what belongs beside it

The count is the answer the builder produces, so it opens the pinned actions bar and carries the only aria-live — the readback sentence is not announced, because that would read someone's own typing back to them. There is no apply and no cancel: every complete condition has already updated the URL, so Show results is the one exit. Link, Embed, API and Feed live in the handoff rail beside the editor, where they stay findable without making the exit bar do two jobs.

Dialog, panel, or page

One rule, so that neighbouring buttons don't behave differently for no reason.

ContainerContentAnchored toHere
Panel a short choice, or one thing to copy its button Add to list, Cite, Share, Save search, filter editor
Dialog a task needing the screen, or a consequence nothing Advanced search, Export, confirmations
Page a surface someone arrives at an address the standalone builder

Two consequences follow. Cite became a panel on 2026-08-10: it hands over one string and sits in the same action row as Add to list, which was already a panel, and two adjacent buttons where one anchors to itself while the other takes over the screen is a difference people feel without being able to name it. A dialog never opens a dialog: if something reachable from inside the builder outgrows a panel, the answer is a step inside the same dialog — a back arrow swapping the body, as the mobile filters tray already does.

When a facet cannot express the condition

A built condition can say things a checkbox list cannot: is not, a range, a pasted batch. Applied filters surface as chips either way (search & filtering, rule 4), and the facet whose dimension is held reports that instead of contradicting it with empty checkboxes.
